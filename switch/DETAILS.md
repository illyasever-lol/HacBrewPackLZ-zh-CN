# hacBrewPackLZ for Switch in detail

Everything the [Switch page](README.md) leaves out.

## Using it

It opens on the **Overview**, and L and R go from there to the two lists:

- **Overview**: how much space you can free, and, for the SD card, the console and a USB drive, a bar of how full each is, with the part compressing what's ticked would free in the accent colour and the free space now and afterwards beside it. Only installed games that get replaced free anything: game files make new NSPs, and installing takes space. Below that is a card for each list: how many games it has and what they take up, what's ticked to do, with what they come to now and afterwards and how much smaller that is. Under that are two buttons that say what they do: one that does what's ticked, such as **Compress 12 games**, and **Choose games**, which opens the list to choose from. Then come the games saving the most, and at the bottom, any installed games an earlier version left saying they need their update, or asking for a newer system version than the console has, which won't start as they are and which A offers to fix, how far measuring has got, or, with Quick analysis, how many games aren't sure yet, either of which A explains, what's done, with what compressing the installed ones has freed, and, when game files are saved as NSPs, the compressed ones whose game isn't installed that way, which A installs. A list with nothing to count says why instead, such as that it's still being looked through, and Game files with nothing found has a button for **Where to look**. A presses the button the pointer's on, or opens the list on the game or line it's on. X does the button of the card the pointer's on, from anywhere on that card: it's the one filled in, with X on it, while the other card's is only outlined. Up and down go through a card, and left and right go to what's beside, or straight across to the other card. A tap puts the pointer on something, and a second tap presses it. How game files get done, installed or saved as NSPs, is in the words, so a setting you've forgotten about shows. Both lists are read from here, the installed games first.
- **Installed games**: what's on the console.
- **Game files**: every NSP, NSZ, XCI and XCZ, and every game extracted to a folder, on the SD card, USB drives, and PCs running `hacbrewpacklz send`, the games on a game card that's in, or in one folder if you choose one. A game card's game says **On the game card**, and is installed compressed or saved as an NSP like any game file, read through the system's own records of the card: the card isn't changed, and the console goes on listing what's on it beside the installed copy. Files a Mac leaves beside others, whose names start with `._`, aren't games and aren't listed. On the SD card, the folders of the system and of custom firmware, `config`, where homebrew keeps its settings, `SaltySD`, and hidden folders are left out, and in `switch`, only each app's folder and the folders straight inside it are looked in, not the app's own things deeper down. **What's left out**, under Where to look while it looks everywhere, says so, and an empty Game files list or card points there; the log says how many folders were left out. A folder you choose to look in is looked through all the way down, and what this made of its games in the folder NSPs are saved in is found with them, so a game from it compressed there is done rather than to do again. A PC on the USB cable is only listed once `send` there has answered. A PC's games come up by themselves as soon as it's heard from, and go when it stops sharing. The PC also works out what's in its files and how small they'd get, which is a good deal faster than reading them across the network. **Where to look**, in the + menu, chooses which of those it looks in. Each game is one entry, with its update and DLC; other copies of it are noted on it, under + → This game → Details. Of copies just as new, the one used is on the SD card, then a USB drive, then the game card, then a PC on the USB cable, then one over the network. A PC on both the cable and the network is only looked in on the cable, which is faster and steadier, unless **A PC on both**, under Where to look, says Wi-Fi first: then it's only looked in over the network. A PC heard over the network before the cable's PC has said its name is read through the cable once it has. Reading a file from front to back, the next piece is asked for while one is worked on, over the cable as over the network, and the PC reads the next piece from its disk while one goes across. The log says, for each file read from a PC, how fast it came and over what. A copy this has already compressed, as new as the original, takes its place, and says "Compressed, not installed yet" until it's installed. An update file on its own, for a game that's installed and older, is listed as an update for the installed game: X makes it part of what's installed, compressed, in place of it, whether that's the original or a copy this compressed, without the original game's file. A copy compressed with an update in it before version 1.5 also needs that update's file beside the new one, and says so; a game its developer compressed takes the original game. See [Updating a game](../docs/help.md#updating-a-game).

**Settings** is at the end of the + menu, with About at the bottom of it, and B goes back to the list.

The first time it's opened, a welcome screen says what it does and asks about the settings most people will want a say in. When compressing: whether to replace installed games or save an NSP of them, whether to install game files or save an NSP of them, and where NSP files go. Then the minimum saving, automatic updates, and sending problems to the developer, which is off unless it's turned on. It only comes up the once, and it can be brought back from Settings.

The first time you see a game it gets analyzed by itself, in the background, which takes about a second and only reads. The answers are remembered, so this only happens once, unless you ask for it again in the + menu. A game that couldn't be read for want of a key or a ticket is the exception: it's tried again each time the app opens, as the keys may have been dumped again since. Keys a `prod.keys` leaves out, such as the key area keys of newer firmware, are worked out from its master keys, the way Lockpick does. Analyzing stops for X while you answer, and goes on by itself afterwards. Then the best savings come first, and you can see for each game what it takes up now, what it would take up after, and what that saves. What's just been done goes to the end of the list, and what's next is at the top. A game that couldn't be done says what went wrong in a few plain words, in red, such as "Damaged: dump or download it again." or "The SD card was busy. Try again.", and the error itself is under + → This game → Details.

The lists come up straight away from what was there last time, and get brought up to date behind that. Only the first time, or for a game that's new or has changed, does anything have to be read for its name and icon. Whichever list is on the screen comes first, so another list that's still coming up stops and picks up again when it's that list's turn. Analyzing doesn't stop for any of that: it goes on beside a list coming up, and once the list on the screen has been analyzed, it goes on with the others that have come up. Whatever gets saved goes on the lists by itself.

In the + menu:

- **Install the ticked games**, from Game files, whatever the settings say to do with them.
- **Details** and **Look inside**, for the game that's selected.

### Spending the time where it counts

Settings to get the most space in the least time, and a list worth looking at:

- **Minimum saving**, 5% to begin with: a game measured to save less than this is settled, under Done, saying it's not worth it and what it saves. A first look from a sample can't say that, as what it can't see only makes a game save more, so a game it puts under the minimum is **not sure yet**, and isn't ticked until it's been read in full. What that finds is kept. You can still tick any game yourself, and it's compressed whatever it saves.
- **Analysis**, Thorough to begin with: after a quick first look at each game, about a second each, analysis goes on, once every list has come up and had its first looks, to read every game in full by itself while the app is open, writing nothing: the games a first look can't vouch for first, then the rest, the smallest first in each, so more get their exact figures sooner and what gives way part way through starts the least over, so every figure ends up exact, and the ones worth it are ticked. It gives way to anything you start, carrying on while a question is up, and goes on afterwards, stops between games for games that have just come up to get their first look, waits while the battery is under 15% and the console isn't charging, and keeps each game's answer as soon as it's found, so stopping part way only loses the game it was on. The lists take their new order as figures come in, once nothing has been pressed for a moment, so nothing moves under the pointer. About 15 seconds a GB from the SD card. **Quick** stops at the first look, and games it can't vouch for stay unticked, unless you tick them.
- **Hide games under 1 MB**, on by default: leaves out games that small with no update or DLC, like shortcuts to homebrew apps on the HOME Menu.
- **Each list opens on the view it was last on**, To do the first time: what's to do, leaving off what there's nothing left to do with, to keep it short, with Done and Everything a press of left or right away. An installed game is done once it's compressed, or once it's measured to save less than the minimum, or has nothing to gain, each saying why. A game file is done once its game is installed compressed, as new or newer, so a compressed file that isn't installed yet stays, ready to install. If game files are set to be saved as NSPs, a game file is done once it's compressed, and the overview offers to install it. With compression off, a repack only gains anything by making a game's update part of it, so a game in one piece is done, whether it was never updated, was merged by another tool, or was repacked here, and it's under Done whenever the app opens. Game files that get installed are done once their game is installed, as new or newer. Left and right show what's done whenever you want, which is how to check one of them.

A game that's in a folder only comes up once, however many NSPs have been made from it. Once one has been compressed, the folder counts as compressed too.

A dump of one of Sphaira's forwarders is on the list like anything else, even though its content meta is cut short: Sphaira records the wrong size for it, so whatever dumped it only took the first 192 bytes. What was in it can be worked out from the program and control data, and whatever gets made from such a file has a whole one again.

A game that's already compressed, or that wouldn't get any smaller, comes up unticked whatever the settings say, except a compressed game file that's still to be installed. The first kind gets the same check as a game that's just been compressed, and the second says there's nothing to gain. Ticked by hand, a game compressed by this version, or with no game data to compress, is still left as it is, and the question before compressing says so, and leaves it out of what it counts. A game sure to save nothing shows no figure, rather than 0 B, or a hair over its size from a margin that could go either way.

### What compressing does

For an **installed game** there's a choice, in the settings:

- **Replace them**, the default, which is what frees the space. Each step can be seen as it happens:
  1. The compressed game is written beside the original, as it's made. Nothing goes through a temporary file.
  2. Its hash gets worked out, from memory for whatever fits there, and otherwise by reading it back.
  3. Only then is the new copy swapped in and the original deleted.
- **Save an NSP**, which leaves the game as it is and frees nothing.

While it works, the game being done has a card of its own, with its icon, the step it's on and how far that's got, and the steps it goes through along the bottom. With more than one game, a list beside it says what each one done so far saved, which one is being done, and what's still to come with its size now, and below the card is how far it's got with all of them, the time left, and what's been freed so far. Afterwards, the results say what was freed and, for the SD card, the console and a USB drive, how much was free before and is now, with the part that was freed in the accent colour, as on the overview. Then every game, those that went wrong first, saying what to try, and the rest with the biggest saving first, each with what it was, what it is now and a bar of how much smaller that is. What went wrong with a game is said in full, however long. A goes back to the list, where what was compressed is under Done.

Every new copy is checked before the original goes: every byte gets read back from the card in step 2 and checked against what was written, and game data read through the new copy gets compared with the original from across the game, which the firmware does itself where it can. That catches a failing card. The read is the one that works out the copy's hash, so checking takes it no longer.

The hash can't be worked out while it's being written, as it starts with the header, which says how everything else came out and so can't be known until all of it has been written. An NCA's name and what the game's records say about it are its hash, so there's no leaving that out. So all of it is read back from the card, ahead of being hashed, and checked on the way. None of it is kept in memory to save reading it: kept that way, it broke the rest of memory up into pieces too small to use, and big games ran out of memory with a gigabyte free. How large a game can be only depends on memory for its hash trees and its table, about 800 MB for one of 160 GB, opened through a game, and it says at the start if there isn't enough.

Once each time it's opened, before the first game that needs it, the console is asked to read a small compressed test copy, so that a console that can't read these finds out straight away, before any time has gone on it. If it can't, nothing else gets done.

For a **game file**, it's installed compressed, or if the settings say so, a compressed NSP is saved in the NSP folder instead. The file itself isn't changed. What's already compressed goes across as it is when it's installed. If you'd rather not keep the file once it's in, **Once a file is installed** in the settings deletes it, but only after the game has been installed and checked, and only when everything in that file has been.

For an **extracted game**, which is a folder holding `exefs` and `control`, and also `romfs`, `logo`, `htmldoc` and `legalinfo` where it has them, an NSP is built and saved in the NSP folder, or it's installed. That's what extracting leaves behind, and also what you can change files in first. Its icon, name and size come from those files. The version comes from the `[v123]` in the folder's name, if there is one. The folder isn't changed.

A base game, its update and its DLC are one row, and all get done. The update becomes part of the game. A game saved as an NSP holds its DLC too, so emulators find it without installing it, and DLC without their game go together into one file. **Game and DLC in one file**, in More settings under What to do with them, is on to begin with. Turned off, it gives each DLC a file of its own, and beside this tool's copy of its game, a DLC with no file of its own gets one. A DLC has one when a copy of it is alone in a file or in a file this tool made. A DLC given without its game that has nothing to compress is left as it is, with the setting off or when it's the only DLC of its game. While it's on and game files are saved as NSPs, a compressed copy that doesn't hold all the DLC on the list is made again with them. That's from the copy, or from the original when that's there, the copy is no newer and a DLC of the game has no file of its own, like one only inside a merged original. Of several copies, the one that holds the DLC is used. Its line says "1 DLC not in its file", and when making it saves nothing it's under Done, where ticking it makes it. If a file holding a game and its DLC, or DLC together, fails to save because something in it is damaged, that's remembered until the files change, and while the setting is on it isn't tried again by itself. Installing keeps each DLC apart, as the console does. A game with more than one program in it, a collection, is compressed like any other. Save data isn't touched. Some base games only hold what their update still reads from them, sometimes with the same version as the update. Those work like any other with their update there, and can't be done without it, which it says.

**An official update installed over a compressed game stops it starting**, since an update is a patch against the original. A newer one than the game makes it a game to do on Installed games, ticked whatever it saves, and compressing it makes the update part of it: the copy stands in for the original, rebuilt from it, or, when it has an update in it already, through the map of where that update kept the original's parts. What comes out is one compressed game at the update's version, in place of both. Analyzing it first checks the update fits what the copy holds, and if it doesn't, says what it takes: the file of the update in a copy made before version 1.5, or the original game. An update that's no newer than the game only stops it starting, which removing it puts right, and that's what it says.

**With compression off**, in the settings, games are repacked just as they are, with an update made part of the game. Everything says Repack rather than Compress. A game with an update can come out a good deal smaller that way, and it can take the place of what's installed like anything else. A game with no update comes out the same size, so it starts unticked, under Done, saying so. If any are ticked by hand, it asks before going on, and they can be unticked, repacked anyway, or the whole thing cancelled with the ticks left as they were.

**Before anything starts**, when you press X, it works out what fits. For a game being replaced, that's room for the new copy beside the old one, and what that frees afterwards counts towards the next, so the order can change to make more of them fit. If some won't fit it says which, and how much more it would take. If none will, nothing starts.

**Checking for damage**, in the + menu, reads all of each ticked game through its hash trees, which takes about as long as copying it. **Extracting** writes a game's files out to the folder chosen for that. While it goes, the game's folder holds `Not finished extracting.txt`, which goes once all of it is out: a folder with it, as the power going part of the way through leaves one, isn't listed as a game, and extracting it again starts afresh. An NSP saved where a file has its name already, such as the game it was made from, is saved as `… (2).nsp`, then `(3)` and on: nothing that's there is written over.

### Folders and USB drives

In the settings, **NSP files go in** and **Extracted games go in** each open a file explorer. A goes into a folder, B back up, X uses the folder you're in, Y goes back to the usual place, which is `sdmc:/hacBrewPackLZ`, and `extracted` inside that, and the - button closes it. Folders holding an extracted game are marked as such.

USB drives work anywhere a folder can be chosen, and their game files are listed with the rest. FAT32, exFAT, NTFS and ext4 can all be used, with the drive plugged into the dock or through an adapter. FAT32 can't hold a file of 4 GB or more, which it says before it starts. If a drive gets taken out, whatever's being written to it fails and leaves a `.part` file, and the original stays as it was.

### How little it reads and writes

A game is read once, its compressed data written once, straight to where it'll stay, and read back once at the end. Compressed blocks only pass through memory on the way. Reading the new copy back works out its hash and checks it at once. A game on the SD card needs room for its compressed size, and nothing more, but for a solid NSZ read with its update, below.

**A solid NSZ or XCZ** is one long stream that can only be read from its start, and read with its update, parts of both are needed out of order: an update's own tables are at its end, and a big update's pieces aren't stored in the order the game is read (Slay the Princess's update went back 120 times, the game 33). What's been read of such a stream is kept aside. It goes in memory from the first time back, if all of it fits in what the game and its update share: about 2 GB opened through a game, and none from the album. An update that only goes back to read its tables, about three times, is just read again from the start. One that keeps going back keeps its start in memory as far as there's room, and the rest in a temporary copy in the temp folder on the SD card, deleted as soon as it's done. The question before installing or compressing says which games can need that copy, and up to how much, and the room it takes is counted with the rest before anything starts. Such a game isn't read in full only to measure it, as that would write the copy for a number: it goes by its first look. Extracting or checking one can make the copy too.

It works on the three of the processor's cores a game gets, and on the fourth if it's been opened in a way that allows it, such as with Sphaira's option for that. The fourth is the one the system keeps for itself and the home menu, which get it whenever they want it, as nothing here ever goes ahead of them, and it's left alone altogether while something else is on the screen. The log says how many it has, on its second line.

Going through folders and reading files is mostly done by the system's own file service, which only ever runs on that fourth core, whatever this does. So while something else is on the screen, like the home menu, everything here reads and writes a good deal more slowly, to keep that core free. It goes back to full speed when it's back on the screen.

### Keeping it up to date

**Keep this app up to date**, in the settings, looks for a newer version each time the app opens, if the console is online, and installs it. It's on to begin with. **Check for updates now** does it once. It only goes to GitLab, and everything it gets is checked against a signature only a real release has. The new version takes over the next time the app opens, or straight away if you choose to restart.

### If something goes wrong

Stopping, a failure of any kind, or the power going all leave the game as it was: the original stays until the new copy has been checked. The app writes down how far it has got, so if the power goes, the next start either undoes what was written or finishes the swap, and tells you it did. Closing it from the home menu stops at a safe point.

A game that's been compressed never asks for a newer version of itself: that's cleared in what gets made, and when it's installed from here, the console is told that the version now on it is the one that counts, which is what a required version reset in other tools does. Nor does it keep the mark a base game cut down to go with its update has, as what gets made always holds all of the game: with that mark, DBI warned that a game needed its update, and it didn't start. Copies version 1.4.3 or older made of such a game kept the mark, so the overview says how many installed games won't start as they are, and A on that line offers to **Fix** them, which takes the mark off the console's record of each and tells it the version there is the one to start. Nothing else is written, and each copy is checked to be all there before anything changes.

The + menu is split into pages, for this game, the ticked games and the list, and B goes back. It can uninstall the game that's selected, or on the other lists, delete its file or folder, or do that to everything that's ticked. It always asks first, naming what's about to go, with keeping it as the choice already selected. Settings starts with what most people change, and **More settings** at the bottom brings up the rest. Uninstalling leaves the game's save data alone. A game that's open can't be uninstalled or compressed, and nor can the one the app was opened through, by holding R on it: start the app from another game for that one.

The welcome screen comes up the first time, and whenever the app's own folder has gone, even though the settings themselves are kept in a second place. It can also be brought up from Settings.

**Keep a log**, under More settings, is on to begin with. When it's on, what it does is written to `sdmc:/switch/hacBrewPackLZ/log.txt`, of this time only, and `opening.txt` beside it says how far opening got, with the system's error codes, and without keys. That's what to look at, or send, if something doesn't work. Some consoles turn the name `log.txt` down for a few seconds as the app opens: the log starts as `log-other.txt` then, whose first line says so, and is renamed `log.txt` once the console lets it, which writes nothing more to the card. If the console never does, it stays `log-other.txt`. As the app opens, the log also says which games the console won't start as they are, as it wants a newer version than the one installed, and which compressed games it offers a newer version of before they start, with the versions it wants.

**+ → Help** has a few lines on each of the usual problems, each with a QR code that opens the rest of it in [Help](../docs/help.md) on a phone. **Report a problem** there asks what you were doing, on the console's keyboard, and sends a report straight to the developer, then says what came of it, such as a problem that's already fixed in a newer version. With no internet, it saves it as `report.txt` beside the log instead. The report has the version, the console, the settings, both lists with what was said about each game, the last job, the last 3,000 lines the app said, whether or not the log is on, and the newest five of Atmosphère's crash and fatal error reports from the last month. Those keep what crashed, the error, the registers and the backtrace, and leave out the memory they copy out, and any register that holds part of a key. Any key's value is taken out of it, should one ever get in. A game that an official update was installed over, after this tool rebuilt it, says on the list that it won't start until the update's made part of it.

**Send problem reports**, in the welcome and in Settings under More settings, is off unless it's turned on. Whoever had the welcome before it was there is asked about it once, the first time this version opens. When it's on, a report goes by itself when a game can't be done, and, the next time the app opens, when it stopped on something it didn't expect, which Atmosphère writes up, or stopped answering until it was closed from the HOME menu. Not answering for half a minute only leaves a note, which goes if the app never comes out of it. Each problem goes once for each version, and after that it's only counted. What's waiting to go is kept beside the log, in `reports waiting`, and turning the setting off drops it. When Atmosphère says a compressed game stopped with an error since the app was last open, it asks whether the game started. It asks the same when the console's play history has one closing within 20 seconds of starting, for a game that closes without crashing, which Atmosphère doesn't write down. It asks about the first one, and only once. If it didn't, it says what usually helps, and sends what happened, or, when the setting is off, offers to send it in one press, with nothing to type.

Settings and what's been worked out are saved in that folder and again in `sdmc:/config/hacBrewPackLZ`, one after the other, so that there's always a whole copy of them. If they can't be saved anywhere, it says so on the screen, with the reason. The log says which files were there when it opened and when it closed, and which copy it went by.

### How analyzing gets through it quickly

A game that's already stored compressed, with no update to make part of it, doesn't take any of this: looking at its header is enough to say there's nothing to gain. Otherwise, its file table gets looked at first, for copies of its own files, which compressing stores once: a file the same size as another, with the same 4 KB from its middle, start and end, or one with the same name and about the same size whose end or start holds much the same. That takes a few small reads, the copies that could hold the most first, and no more than a quarter of the time. What else a game holds again by itself, such as what level packs have in common, only reading all of it finds, so a game can come out smaller than its row says, and a first look never leaves a game out on its own say. Then part of each game gets really compressed, from all across it, leaving the copies out. What a game saves is shown as at least what the sample is sure of, as what it can't see only ever makes a game save more, and the minimum saving goes by that. Every processor core keeps going between reading a piece and compressing it, so neither ever waits for the other. Pieces are read in order, so a hard drive on USB sweeps across rather than jumping about, and one at a time, unless timing the first few shows that reading several at once gets more read, which is up to what it's stored on and not to what it says it is. Installed games are read straight from the file system rather than through the system's content manager, if it lets it, as a game with an update is read from two files in turn. It stops as soon as the answer is good to about 2%, or after about a second, or a little longer if it's still reading what it takes to say anything at all.

A game a first look puts under the minimum, or says would gain nothing, is not sure yet, and isn't ticked, as it may save more. Reading all of it, writing nothing, says what it saves, counting everything that's stored once, compressing every 16th block to measure the rest by and checking the game's own hashes. A game under 1 GB has every block compressed, which takes about twice as long, so its figure is exact to the byte; one measured before that is read once more, in turn. Analysis does that by itself, as above, and the line on each card of the overview says how far it's got, such as "Measuring for exact figures: 12 left", with about how long that takes, at the speed this console has been reading, less what's been read of the game it's on; A on it says what it is, and turns it off. The bar along the bottom goes by the game data read, as games differ in size by thousands of times. Compressing does only the ticked games, and its question says how many not sure yet are still to be measured, as they may be ticked afterwards. With Quick analysis, they stay unticked, and the line says Thorough analysis measures them; ticked by hand, one is compressed whatever it saves. A PC sharing the game measures it itself, from its own disk.

Two things are asked when they first matter, each saying where to change it later: deleting the files once the first install from them has kept them, asked the once, over what came of it, with A keeping them; and, whenever the SD card hasn't room for games to install and the console has, putting them on the console that time instead.

A compressed game says what compressing it freed: a copy this makes says what the game came to before, in a small file in its control data, beside its name and icons, where nothing else looks, along with the version that made it. One compressed by a version before 1.5, which didn't store what a game holds more than once only once, is looked at like any other installed game, and stays under Done as it is, saying what it freed, until compressing it again is sure to be worth it, from its first look or once it's been read in full: then it's to do, and ticked. A game its developer compressed says so. Installed, it's worked out and measured like any other game, and says what compressing it again here saves, but it's never ticked by itself: compressed again, an update needs its original game file, as an official update reads the bytes its developer stored, which can't be made again. Ticked by hand, it's compressed, and the question before compressing says that first. An installed game with nothing in it compressed, such as one with all its data in its program, says there's no game data to compress. A copy this tool made is known by what's in it, not by its name: its game data is stored compressed under the oldest key generation, where a game its developer compressed, which needs firmware 12 or later, never is. That holds for copies made by every version, including 1.0 to 1.3, which put that data after the levels that check it.

### How the lists come up quickly

There's no reading the card's own tables from here the way Everything does on Windows, but the idea is the same: answer from what's already been noted down, instead of going to the disk. What's in each game file is noted down the first time it's seen, with its icon. After that, bringing the lists up to date only takes going through the folders, a level at a time with all the cores working on it, and asking for nothing but names, and only a file that's new or has changed in size gets opened. **Refresh the list** in the + menu looks at all of it again. A big USB drive, or a PC sharing a lot, can take a while: while the list on the screen is being looked through, B stops looking, and what's been found by then stays, ready to work with, until the list is refreshed. Opening one takes a few small reads, several at a time. Its hash trees don't get read for it, as all it's after is a name and an icon. Nothing else about a game file gets opened until there's something to do with it. Installed games work the same way, and the names and icons of those it hasn't seen get read several at a time as well.

## What's been learned on a console

- With Atmosphere, everything the app reads and writes goes through its fs.mitm module. When the kernel turns one of the app's requests down before fs.mitm gets it, fs.mitm goes on waiting for that request, and a wake-up of its own can end the wait in a way it doesn't expect, which aborts it and takes the console with it. So a request that's turned down is asked once, then tried again later rather than straight away, and the app only has a few going at once. It only costs a little, as the file service runs on one core anyway.
- Creating and opening files was turned down at times with 2001-0106. That code is an invalid memory state, not being out of handles (2001-0105), though it was long taken for that. The system's library sends a path as 769 bytes from wherever it starts, however short it is, and the kernel turns the request down unless the app can read all of them. So a short path that sat just below memory the app couldn't read at that moment, such as where a thread's stack is mapped from, was turned down. Paths now go from a buffer of that size, as the library's own file functions do. The log says when a request is turned down, with how many times.
- If the console goes down part way through writing, the SD card can be left with its allocation table half done, which only a disk check on a PC puts right. So a file being written gets its room set aside a gigabyte at a time rather than all at once, what's written is flushed every 256 MB, both to the card and to the console's own storage, and a job stops before the next game once the battery is under 15% and the console isn't plugged in.
- Each file or folder created or deleted on an SD card takes several milliseconds, so a game with thousands of small files takes minutes to extract or delete, whatever the processor does.
- A crash or a hard reset can lose files that were open at the time, which may be why settings and logs went missing.

## What's where

## Building

With devkitPro's `switch-dev`, `switch-curl`, `switch-ntfs-3g` and `switch-lwext4`:

```
make
```

That gives `hacBrewPackLZ.nro`. Unlike libnx's template, the Makefile leaves exceptions and RTTI on, as the engine uses them.

USB drives are read with [libusbhsfs](https://github.com/DarkMatterCore/libusbhsfs), [NTFS-3G](https://github.com/tuxera/ntfs-3g) and [lwext4](https://github.com/gkostka/lwext4), and the updater and Report a problem use [curl](https://curl.se). libusbhsfs's source is in `third_party`, and the others come from [devkitPro's packages](https://github.com/devkitPro/pacman-packages). The first three are under the GPL, version 2 or later, which fits this tool's own GPL-2.0.

## Testing on a PC

`host\build.cmd <output folder>` builds these with Visual Studio's compiler. `host\build_fast.cmd <output folder>` builds the same with the Ninja that comes with Visual Studio: in the same folder again, it only compiles what changed and every file that includes a header that changed, and the test programs' own code isn't optimized, so a change to a test builds in seconds.

| Program | What it's for |
|---|---|
| `hbptool` | The engine on its own, with commands like the PC tool's. `tests\matrix.py engine` compares its output with the PC tool's, byte for byte, on every format and setting. Point `HBPTOOL` at it |
| `replace_test` | Replaces games on the pretend console, and loses power at every step along the way, and again during the recovery. Whenever that happens, the game has to stay whole, nothing can be left behind, and it has to work when tried again. With `--once` it replaces what's given a single time, with no power cuts, and fails if that throws or leaves the game not whole: for a big game, or one with more than one program in it |
| `app_test` | The whole app with a pretend person pressing the buttons, against the pretend console, with screenshots to look at |

```
replace_test -k prod.keys <folder> [--stride N] base.nsp update.nsp [dlc.nsp]
replace_test -k prod.keys <folder> --once game.nsp [update.nsp...]
app_test -k prod.keys <folder> <screenshots> demo
app_test -k prod.keys <folder> <screenshots> real base.nsp update.nsp [other.nsp]
app_test -k prod.keys <folder> <screenshots> check [seed] [steps] base.nsp update.nsp dlc.nsp other.nsp [more game files...]
```

`demo` fills the screens with made-up games to look at. `real` goes through everything with real ones: analyzing and analyzing again, compressing, starting again with everything remembered, a firmware that refuses, no room or only some, stopping, a power cut, the minimum saving, hiding games, saving and installing game files, DLC going into a game's file, or with no game into one file, or with the setting off into a file each, a copy without its DLC made again with it, deleting them afterwards, extracting, extracted games and choosing their folder, installing from the menu, a USB drive coming and going, repacking in place or to a file, the checks turned off, settings kept or not being able to be saved, and the buttons. With `UPDATE_DIR` set to a folder holding what `tools\sign_release.py` makes for a `program.bin` of version 9.9.9, it tries updating too, with bad signatures and damaged downloads.

`check` checks the app against itself instead of against a script. A pretend person changes settings, ticks games, sorts and runs jobs in an order that comes from the seed. After every step:

- A fresh start of the app, with the same files, console and settings, has to show the same lists. That includes the same games, hidden or not, in the same order, saying the same things, with the same sizes and ticks.
- Every few steps, a start with nothing remembered has to come to the same sizes, within their margin.
- What each game file's row says it comes to is checked against what converting it really comes to. A row whose estimate read all of its game data, so has no margin, has to be as close as `tests\matrix.py` holds small titles to.
- A question that says something about games, such as their coming out the same size, is checked against their rows.

`other.nsp` should be a game that compresses well. It goes on the pretend console as it is, and on the SD card as a compressed copy. Any more files go on the SD card beside the first three: give it a game whose update holds part of it more than once, from `tests\make_patch_test.py`'s `shared` variant, one that also holds some of its own data again, from its `repeats` variant, and a game compressed by Nintendo with its update, as described in `tests\README.md`. Run several seeds: each one takes a different path.

The pretend console behaves as the real services do as far as is known, but it isn't one. What can only be found out on a console is whether `nx_console.cpp` has understood those services right.
